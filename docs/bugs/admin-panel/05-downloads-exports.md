## 2. Password-protection mechanism — what exists, what lacks it, and the deletion gap

- **Mechanism exists and works:** `src/services/backup_manager.py:255-286` `pack_backup(data, password, hint)`. With a password it derives per-file salt keys (`_derive_keys`), encrypts with AES-GCM, and HMAC-signs (`:266-274`); without, it emits `MAGIC_UNPROTECTED` with only a server-side HMAC (`:275-284`). So "pack with password" is a solved problem for the `.fsback`/`.fspback`/`.fsb` family only. Plain CSV/ZIP/log sends (E1–E4, E6) have no such wrapper and would need one (e.g. password-ZIP) built.
- **Which exports lack it:** E1, E2, E3, E4, E6 send files with **zero** password step — 5 of the 6 admin file-sends. Only E5's `.fspback` branch is protected. Demand is "EVERY data download must be password-protected" → gap covers E1–E4, E6 plus all 7 demanded-but-missing downloads.
- **Password-message deletion: ABSENT everywhere (confirmed).** A search for `export_password|admin_getdata_password|EXPORT_PASSWORD` combined with `delete_message` returns zero hits. Neither `export_password_text_handler` (`src/handlers/export.py:1798-1867`) nor `admin_getdata_password_handler` (`src/admin/handlers.py:3136-3167`) calls `delete_message`/`delete()` on the admin's password/hint messages; both only `reply_text` prompts and store plaintext in `context.user_data` (`export.py:1817,1837`; `handlers.py:3147,3157`). The typed password therefore **persists indefinitely in chat history** (and in Telegram server history / notifications) for every protected export today. Any fix must delete both the admin-sent password message(s) and the bot's echo/prompt as soon as the pack succeeds (or fails/cancels).

## 3. Datetime formatting — UTC vs Asia/Yerevan

- **Storage is UTC:** ratings `created_at = datetime.now(TIMEZONE).isoformat()` (`src/callbacks/user/ratings.py:38`); audit entries same (`src/core/security.py:346-351`); issue records use `datetime.now(timezone.utc)` (`src/admin/helpers.py:496,527`); user `first_seen`/`last_seen` likewise. With no env override, `TIMEZONE` is UTC.
- **Helpers:** `localize_datetime(dt)` (`src/core/helpers.py:533-541`) attaches/converts to global `TIMEZONE` (UTC); `get_user_timezone()` (`:544-557`) falls back to `TIMEZONE_NAME` (UTC). Neither targets Asia/Yerevan. Per-channel/user tz selection exists (`get_channel_timezone`, `format_channel_tz_display` at `:588-767`) but no export path calls it.
- **Every export renders UTC without conversion or label:** E1 (`export.py:1212-1238`), E2 (`bulk.py:116`), E3 (`token.py:78`), E4 payload, E5 `_meta`/records, E6 filename/caption. Display screens slice `timestamp[:16]` / `expires[:10]` (`analytics.py:101,122,188,259`; `ratings.py:59`).
- **The single Yerevan exception proves the rule:** `_build_issue_text` (`src/admin/helpers.py:348-403`) hard-codes `_ZI('Asia/Yerevan')` for the "now" header line (`:353-357`) but the actual error `timestamp` stays a UTC iso string. So even the one Yerevan-aware line does not fix the logged time.
- **Impact:** every timestamp an admin downloads today is UTC presented as if local; a +4h skew vs Asia/Yerevan on every row. Fix = convert at render/export time with `ZoneInfo('Asia/Yerevan')` (or the complainant's per-admin tz) and append an explicit `+04:00` / `AMT` label; never mutate stored values.

## 4. Issue log vs security log stores — is the "actual issue" stored?

**Yes — the full text IS stored; the admin screen just never shows it (render-layer bug, not storage loss).**

- **Issue record** (`src/admin/helpers.py:493-540` `report_issue`): `{title, severity, user_id, details (full traceback, tokens redacted via `_redact_tokens` at `:489-491`), timestamp (utc iso), before_actions[10], err_preview (first 1500 chars, `:499-501`), msg_ids, fixed, after_actions (appended async by `_append_after_actions`, `:406-486`)}`. Persisted in encrypted domain `issue_log` (`src/core/botdata.py:70,571-573`; file `data/admin/admin_issue_log.json`, `src/core/config.py:183`). `collect_issues` (`helpers.py:210-223`) returns `details` too.
- **But the screen drops it:** `handle_admin_issue_log` (`analytics.py:92-108`) renders only `severity + timestamp[:16] + title[:80]` (`:101-104`). `details`/`err_preview`/`before_actions`/`after_actions` are never rendered and there is no download. The complaint "shows only part of the issue not the actual issue" is exactly this: the most diagnostic field exists in the DB and is one line away from the renderer.
- **Security/audit store:** `audit_log` entries `{admin_id, action, details, timestamp}` (`security.py:346-351`; file `data/admin/admin_audit_log.json`, `config.py:184`). `collect_security_events` (`helpers.py:716-741`) is a **derived filter**, not its own log: audit rows whose action contains FAIL/BLOCK/SPAM/DELETE/DENIED **plus** ERROR/CRITICAL issues. Screen (`analytics.py:179-202`) truncates to `action[:40]` / `details[:60]` and caps at 20 rows. No download exists. Note the filter silently drops INFO-level admin actions from the "security" view — a download should offer both the filtered view and the raw audit log.

## 5. Feasibility of each demanded download (all feasible; data already assembled)

- **Ratings download — FEASIBLE, trivial.** Store fields: `rating, review, user_id, username, first_name, created_at` + `admin_reply{text,media,admin_id,created_at}` (`ratings.py:32-39`; `callbacks/admin/ratings.py:170-176`). Screen aggregation (avg + 1–5 distribution + latest 5) already computed at `ratings.py:23-37`. Only missing piece is serialization (CSV + styled HTML) + password wrap.
- **Stats download — FEASIBLE.** Raw tables in `data/stats.db` (`src/services/stats.py:18,80+**: sent_messages, message_views/reactions, automated_reports`) with per-user getters `get_sent_messages` (`stats.py:368`) and `get_message_stats` (`stats.py:1043`); per-user counters in `bot_data.user_stats`; revenue via `collect_revenue_stats` (`helpers.py:693-713`). Current `export_stats_csv` is a 6-row summary (`export.py:1210-1217`), not the demanded stats export. Needs a real per-user/per-day dump.
- **Sender-bots list + usernames — FEASIBLE, no new collection needed.** `token_manager.get_tokens()` returns `{token, bot_username, bot_id, channel_id, created_at, updated_at, hide_channel, management{...}}` (`token_manager.py:219-261`); `collect_bot_fleet()` already shapes `{user_id, bot_username, channel, subscription, is_hidden, is_valid, created_at}` (`helpers.py:661-690`). `/getdata` already exports per-user bot metadata **minus the secret** (`handlers.py:3089-3095`: `{k:v ... if k != 'token'}`). Design decision required: global bots-list export must likewise **redact `token`** (usernames + owners + validity are safe; raw tokens must never be downloadable).
- **Expiring-premium list — FEASIBLE, zero new queries.** `collect_expiring_premiums(days=7)` (`helpers.py:744-770`) already returns `{user_id, name, expires, days_left}` with correct iso parsing (`fromisoformat`, naive→TIMEZONE). Only the window (7d) and the missing download need work.
- **Security-log + issue-log downloads — FEASIBLE.** Both collectors exist (`collect_security_events`, `collect_issues`, `collect_audit_log` at `helpers.py:210-223,645-658,716-741`); only pagination cap (20 rows on screen) must be lifted for export (use `limit=100000`-style full pull as `/getdata` already does for analytics at `handlers.py:3083`).
- **Download-everything / multi-format incl. styled HTML — NOT present, must be built.** No "export all" bundle exists for admins (closest is E4's unprotected `.fsb`); no per-section "separate" downloads for the 7 missing datasets; no HTML renderer exists (parsers only do TXT/CSV/JSON/RTF/ODT). The "different messages, beautiful styled HTML" demand implies new per-export caption/success strings (admin translations) plus a shared HTML-report builder — greenfield work, but every underlying dataset is already collected.

## 6. Gap list (severity + impact)

| # | Gap | Severity | Impact |
|---|-----|----------|--------|
| G1 | 5 of 6 admin file-sends unprotected (E1–E4, E6); only `/getdata .fspback` has a password path | **Critical / security** | Any admin-chat compromise or forwarded file leaks full user lists, message metadata, DB backups, logs. Directly violates the "EVERY download password-protected" demand |
| G2 | Password/hint messages never deleted (both user-export and `/getdata` flows) | **Critical / security** | The secret protecting G1's fix stays readable in chat history forever; Handy-notification previews leak it further |
| G3 | All export timestamps UTC, unlabeled; no Asia/Yerevan conversion anywhere in downloads | **High / correctness** | Every downloaded time is off by +4h for the complainant; expiry/first-seen/last-seen decisions made on wrong times |
| G4 | No downloads at all for: ratings, stats (beyond 6-row summary), sender-bots list, expiring-premiums, security log, issue/audit log | **High / feature** | The bulk of the complaint; admins must screenshot 20-row screens |
| G5 | Issue-log screen shows title-only (`title[:80]`), hiding stored `details`/`err_preview`/action trails | **High / diagnosability** | Admins cannot triage from the panel despite the data existing; "only part of the issue" complaint verbatim |
| G6 | No HTML export format; no styled/beautiful exports; generic captions | **Medium / UX** | Blocks the "beautiful styled HTML … multiple formats … different messages" demand entirely |
| G7 | No download-everything bundle (separate or all-at-once) | **Medium / feature** | Admins repeat 4+ manual exports; E4 backup is full-DB but unprotected (G1) and machine-format only |
| G8 | Display caps (20 rows) with no paginated/full export path for issues/security/fleet/expiring | **Medium** | Large fleets/incidents silently truncated; exports must bypass the screen limit |
| G9 | Security-log view is a lossy derived filter (keyword match) with no raw-audit download | **Medium** | INFO-level admin actions invisible in the "security" framing; audit completeness unprovable |
| G10 | Sender-bot `token` present in `get_tokens()` output — a future bots-list export must redact it (as `/getdata` already does) | **Medium / security** | One careless serializer turns a legit feature into a full fleet-takeover leak |

Suggested fix order: G1+G2 (password-wrap every send + delete password messages) → G3 (Yerevan conversion + labels) → G5 (render stored issue details) → G4/G8 (one password-protected exporter per dataset reusing existing collectors) → G7/G6 (bundle + HTML builder + new strings) with G10 as a hard redaction rule in review.
