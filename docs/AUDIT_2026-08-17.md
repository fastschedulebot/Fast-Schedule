# 🔍 FULL CODEBASE AUDIT — Fast Scheduler & SetDate ecosystem

**Date:** 2026-08-17
**Scope:** ALL of `src/` (≈46.5k Python lines), `SetDate/`, `run.py`, `web_server.py`, `translations/` (en.json, ru.json, admin/en.json, SetDate bundles), tests inventory.
**Method:** 9 parallel audit subagents + direct manual verification of every CRITICAL/HIGH claim (I re-read the exact code at every cited line). Findings marked **[VERIFIED]** were confirmed by me personally re-reading the code; **[AGENT]** were reported by audit agents and are highly plausible but not personally re-checked line-by-line.
**Purpose:** FIND ONLY — nothing was fixed. This is the backlog for the next fix sessions.

Verdict: the codebase is feature-rich and well-tested (225 pytest + 21 sim suites), but has a systemic **event-loop blocking** problem, several **money-adjacent payment defects**, **RBAC escalation paths** in the fresh channel-admins feature, and a **PTB v22 dispatch trap** that makes several buttons dead or crashing. Priority order at the bottom.

## 📛 CRITICAL (fix first — money, data loss, or crash)

### C1. Whop webhook grants premium up to 5× per single purchase — zero idempotency [VERIFIED]
- **Where:** `src/web_server.py:107-121` + `src/payments/__init__.py:1295-1319` (`grant_premium_from_whop_webhook` → `extend_user_premium`).
- **What:** `grant_events` accepts **five** event types for the same checkout: `subscription.activated`, `subscription.created`, `transaction.completed`, `transaction.paid`, `checkout.completed`. Each independently calls `extend_user_premium(telegram_id, days)` which **stacks** (premium.py:70-71: `start = current_expires if current_expires > now else now; new = start + days`).
- **Why:** Whop fires several of those events per one real purchase; no `event_id`/`transaction_id` dedup store exists anywhere.
- **Impact:** A single purchase grants 2–5× the paid duration (revenue loss). No amount/currency validation either — any signed `transaction.completed` grants.

### C2. Whop webhook is replayable — signature has no timestamp freshness check [VERIFIED]
- **Where:** `src/payments/__init__.py:950-1008` (`verify_whop_signature`).
- **What:** HMAC-SHA256 over `f"{ts}:{body}"` verified with `compare_digest` — **correct** per Whop v3. But the parsed `ts` is never compared to current time (no replay window enforcement).
- **Impact:** any captured signed webhook replays indefinitely, each replay extending premium again (multiplies C1).

### C3. CryptoBot webhook: `invoice_paid` delivered at-least-once → stacked premium + unpack crash [VERIFIED]
- **Where:** `src/web_server.py:133-165`; `src/payments/__init__.py:1326-1353` + `extract_user_id_from_cryptobot_payload` (1232-1234).
- **What:** (a) `grant_premium_from_cryptobot_webhook` extends unconditionally with **no invoice_id dedup** → every redelivery (CryptoBot retries on 5xx) stacks a full period. (b) `extract_user_id_from_cryptobot_payload` returns bare `None` when the invoice payload is empty, and `web_server.py:160` does `telegram_id, plan = ...` → **TypeError: cannot unpack non-iterable NoneType → 500 → CryptoBot retries forever**; the graceful "No user_id - ignored" branch (161-163) is unreachable.

### C4. Admin custom-expiry-date premium grant crashes with TypeErrors [VERIFIED]
- **Where:** `src/payments/__init__.py:862-864` (`datetime.strptime(text, '%Y-%m-%d')` = naive) compared to `datetime.now(TIMEZONE)` (aware) → `TypeError` on Python 3.11; only `except ValueError` (878) exists. Same class at `:917`/`:934` (`_set_premium_with_start` with naive `start_dt`).
- **Impact:** the whole custom-date grant admin flow is unusable (and any other path seeding a naive `premium_expires` infects models.py — see H-models).

### C5. Admin feedback "media-only reply" crashes with NameError `admin_id` [VERIFIED]
- **Where:** `src/callbacks/admin/feedback.py:169-170`.
- **What:** `safe_reply_text = escape_html(thread_last or t(admin_id, 'admin_feedback_media_only'))` executes at 169, but `admin_id` is only bound by `for admin_id in ADMIN_IDS:` at 170.
- **When:** exactly when the user replies with **media only** (media replies store `text: ''`, so `thread_last` is falsy → the `t(admin_id,...)` branch is evaluated) → NameError → admin never notified → global error handler then spam-messages all admins (H-web).

### C6. `show_sender_bot_home` crashes for every non-owner RBAC admin — UnboundLocalError [VERIFIED]
- **Where:** `src/bots/helpers.py:92`.
- **What:** the RBAC channel-admin branch (line 87-98) calls `get_sender_bot_keyboard(user_id, channel_id, is_subscribed, page=page)`, but `is_subscribed` is **only assigned at line 106, inside the `if is_true_owner:` branch**. Non-owner channel admins opening a sender bot → `UnboundLocalError` → global error handler → "An error occurred. Please try again."
- **Note:** the sync variant `sender_bot_home_keyboard` (line 31) correctly takes `is_subscribed` as a parameter — the async variant forgot it.

### C7. Scheduled-message restore assumes ONE datetime format — mixed-format stores silently lose jobs on restart [VERIFIED]
- **Where:** `src/register.py:951`: `dt = datetime.strptime(msg_data['datetime'], '%Y-%m-%d %H:%M:%S')`.
- **What:** the live store contains both `'2026-08-14 21:14:00'` (old writers) and `'2026-12-26T09:30:00+00:00'` ISO (written by `schedule_conv.py`/`commands.py` datetime_obj paths). The ISO entries raise `ValueError` inside the `for job_id, msg_data` loop → caught at 969 → **job neither restored nor removed** → scheduled posts silently stop firing after restart with no user notice. (The "expired" branch at 956-968 also deletes parse-FAILED future messages only coincidentally.)
- **Impact:** silent permanent loss of scheduled posts for users with ISO-format entries.

### C8. Staged "delete all users" pipeline is dead — PTB job callback signature mismatch [VERIFIED]
- **Where:** `src/services/scheduled_purge.py:110`: `async def _stage_job(application, job)` registered via `run_once(_stage_job, ...)` (126/138).
- **What:** PTB v22.8 job callbacks receive **one** argument (`context`), verified in `telegram/ext/_jobqueue.py:1010` (`await self.callback(context)`). `_stage_job` demands two → `TypeError` every fire.
- **Impact:** the +24h re-ask (stage 6) and +30d final ask (stage 7) from `callbacks/admin/data_delete.py:197/307/366` never fire; `pending_deletions.json` entries stall forever; admins never get the confirmation keyboards.

### C9. ffmpeg/ffprobe run synchronously on the shared event loop — up to 300 s fleet-wide freeze [VERIFIED]
- **Where:** `src/services/media_compress.py:176-181` (`subprocess.run ffprobe, timeout=30`), `:324-332` (ffmpeg encode, `timeout=300`), `:405` (audio, 120), `:46` (`_ensure_ffmpeg`), all inside `async def`s with **no `run_in_executor`/`to_thread`**.
- **Impact:** ONE user compressing a video blocks the single event loop shared by the main bot AND every sender bot for up to 5 minutes — scheduled sends, webhook/polling dispatch and all other users stall. The worst event-loop violation in the codebase (RULE 15 violation).
- **Related (same file):** no size check before `download_as_bytearray()` (H-media) — with a 2 GB local Bot API the loop freeze + 2 GB RAM allocation combine.

### C10. Token decryption failure returns the *ciphertext* as the bot token — key rotation = mass disconnection [VERIFIED]
- **Where:** `src/services/token_manager.py:59-68` (`_decrypt_entry_token`), `src/core/security.py:115-134` (`decrypt_token`).
- **What:** on GCM auth failure `decrypt_token` returns `None`; `_decrypt_entry_token` then **leaves `entry['token']` as the base64 ciphertext**, and every caller (`get_token`, `list_tokens`, `check_token_validity`, bot_manager) treats it as the real token. With a rotated `TOKEN_ENCRYPTION_KEY`, `_check_bot_token_valid` fails for all bots → `_notify_bot_dead` **deletes every user's tokens** → mass sender-bot disconnection. Fail-open also when the key env var is missing (`security.py:117-118` returns ciphertext "as-is").
- **Root cause:** no error marker distinguishes "failed to decrypt" from "decrypted"; key rotation has no re-encryption pass.

### C11. Restart migration clobbers the CURRENT FS-DB store with STALE legacy JSON, every boot [AGENT — high confidence]
- **Where:** `src/core/botdata.py:230-248` (`_migrate_json_to_db_async`), invoked `register.py:1069` on **every** start; no mtime/version check (`_migrate_legacy_global_dir` at :135 is mtime-aware, this one is not).
- **Evidence:** live `data/users/user_settings.json` (159 B, 1 legacy user) vs `data/global/user_settings.json` (1183 B, 3 current users) — boot rewrites the good file from the stale one.
- **Impact:** restart regresses state; crash right after boot = lost settings/referrals/premium written since the last save.

### C12. Encrypted-domain load failure = silent data wipe on next save [AGENT]
- **Where:** `botdata.py:458-489`, `security.py:497-514`.
- **What:** if `FILE_ENCRYPTION_KEY` changes/absent, decrypt returns `{}`; the next `save_all()` writes `{}` over the still-recoverable ciphertext. `issue_log` + `user_actions` destroyed irreversibly. No fail-closed/quarantine.

### C13. Rate-limit gate: raw key text sent to users (`block_reason_default`, `admin_unsupported_lang_notification`) [VERIFIED]
- **Where:** `src/web_server.py:311`, `src/callbacks/admin/users.py:420` use `t(..., 'block_reason_default')`; `src/core/lang_sync.py:55` uses `t(..., 'admin_unsupported_lang_notification')` — **neither key exists in en.json, ru.json or translations/admin/en.json** (verified by exhaustive flatten scan).
- **Impact:** blocked users and admins receive the literal strings `block_reason_default` / `admin_unsupported_lang_notification`.
- **Note (corrected):** `rate_limit_global` (rate_limit_gate.py:45/70) DOES resolve via the **rating section** `rate.limit_global` — text is correct but sits in the wrong category; `stars_payment_sent_prompt` call sites use the correct dotted form `premium.stars_payment_sent_prompt` and resolve fine (the 2026-08-12 fix holds).
